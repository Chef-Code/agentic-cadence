# Tasks 33-37 Roadmap

> **For agentic workers:** Use `docs/roadmaps/2026-06-12-tasks-33-37-roadmap.md` as the public planning artifact after Tasks 28-32. Implement each task on its own branch and update the living docs with evidence before merge.

**Goal:** Move Agentic Cadence from exact operator-approved Git/PR and review-response writes toward review-loop closure and full PR-cycle evidence, without granting autonomous merge, release, package-publication, distributed-lock, role-assignment, agent-pool, paid-review, or continuous-loop authority.

**Architecture:** Cadence remains the governor. The next slices should preserve the existing pattern: consume saved evidence, produce a read-only approval target, execute only exact operator-approved side effects, audit those side effects, refresh read-only GitHub evidence, then compose the resulting chain into reviewable packets before any future merge or continuous-loop work.

**Tech Stack:** Python 3.11+, stdlib CLI, local JSON packets, append-only local audit evidence, Git, optional `gh` only for explicit read-only evidence capture or exact operator-approved GitHub materialization paths, `unittest`, GitHub Actions.

## Phase Ladder

Tasks 33-37 deliberately close the approved PR review loop before any merge or continuous runner exists:

1. **Phase 5 review closure planning:** turn refreshed unresolved review-thread evidence into exact, read-only thread-resolution approval targets.
2. **Phase 5 approved review closure writes:** resolve only exact approved review threads and audit the result.
3. **Phase 5 post-resolution refresh:** extend the post-write evidence gate so thread-resolution results must be followed by fresh saved PR/review evidence.
4. **Phase 1/4/5 PR-cycle composition:** compose the saved local executor, Git/PR, review-response, thread-resolution, and post-write evidence into one replayable PR-cycle packet.
5. **Phase 6 merge decision planning:** produce a read-only merge decision plan from fresh evidence without merging.

## Task 33: Add Review-Thread Resolution Planning

**Status:** Planned.

**Phase:** Phase 5 review closure planning after approved review responses and post-write evidence refresh.

**Why now:** Task 31 can post approved PR body/comment responses, and Task 32 can refresh PR/check/review-thread evidence afterward, but Cadence still treats review-thread resolution as unsupported. Before any thread can be resolved, Cadence needs a read-only packet that proves which exact review threads are eligible, current, unresolved, tied to the refreshed PR head, and safe to present as an approval target.

**Likely files:**
- Modify: `codex_cadence/review_response.py`
- Modify: `codex_cadence/github_evidence.py`
- Modify: `codex_cadence/cli.py`
- Test: `tests/test_pr_readiness.py`, `tests/test_cadence.py`
- Docs: `README.md`, `docs/protocol.md`, `docs/implementation-slices.md`, `docs/progress-log.md`

**Implementation outline:**
- Add a read-only command such as `review-thread-resolution-plan`.
- Consume fresh saved PR JSON, saved review-thread JSON, the relevant `review-response-materialization.v1` result, and optionally a `post-write-pr-evidence-gate.v1` packet.
- Require explicit target thread IDs and bind each target to PR number, branch, base, head SHA, review-thread evidence checksum, prior response materialization checksum, and target checksum.
- Block stale saved PR evidence, incomplete review-thread pagination, outdated threads, already resolved threads, non-actionable summary-only comments, mismatched PR/head anchors, missing response materialization evidence, or target threads that were not part of approved response evidence.
- Emit `review-thread-resolution-plan.v1` with `github_write_started: false`, `operator_confirmation_required: true`, and an approval target checksum.
- Do not call GitHub, resolve threads, post comments, edit PR bodies, invoke paid review, start executors, create branches, commit, push, merge, release, or publish packages.

**Validation:**
- Fresh unresolved current review-thread evidence can produce a resolution approval target.
- Already resolved, outdated, incomplete, stale, wrong-PR, wrong-head, or unresponded-to target threads block before approval.
- Duplicate same-target requests collapse into one planned resolution action.
- The command remains read-only and emits no GitHub command trace.

**Likely files:**

**Implementation outline:**
- Add a command such as `review-thread-resolution-materialize` that consumes `review-thread-resolution-plan.v1` plus an exact target-bound HMAC approval token.
- Use a new purpose-specific approval secret such as `CADENCE_REVIEW_THREAD_RESOLUTION_APPROVAL_SECRET`.
- Recheck saved PR freshness, PR number, branch, base, head SHA, review-thread completeness, target thread IDs, unresolved state, plan checksum, target checksum, and prior response materialization checksum immediately before any `gh` write.
- Resolve only the approved thread IDs through the narrow GitHub mutation path.
- Emit `review-thread-resolution-materialization.v1` with command trace, GitHub thread IDs, resolution status, blockers, `github_write_started`, approval target evidence, and limitations.
- Append replayable `review_thread_resolution_intent` and `review_thread_resolution_result` audit records.

**Validation:**
- Matching plan and approval resolve mocked thread targets and append intent/result audit records.
- Missing approval, wrong approval target, stale PR evidence, head drift, already resolved thread evidence, failed `gh` mutation, or partial write failure emits stable blockers and does not claim merge readiness.
- Audit append failure blocks before GitHub writes or returns recovery evidence if failure happens after a started write boundary.
- Thread resolution remains exact and does not infer that all review feedback is fixed.

- Require fresh `github-evidence-sync` output after the resolution write and verify PR number, branch, base, head SHA, and target thread IDs.
- Re-run PR readiness and candidate discovery from refreshed saved evidence.
- Preserve the existing bounded recommendations: `ready_for_review`, `refresh_required`, `follow_up_candidates`, `wait_for_checks`, `respond_to_review`, or `operator_review`.

## Recommended Order

1. Task 33 creates exact read-only review-thread resolution approval targets.
2. Task 34 resolves only exact approved review threads with audit evidence.
3. Task 35 forces fresh read-only PR/review evidence after thread resolution.
4. Task 36 composes the approved PR-cycle evidence chain into one packet.
5. Task 37 plans merge readiness without granting merge authority.

## Boundaries For All Five Tasks

- No autonomous branch creation, commit, push, PR create/update, review-comment write, PR body update, or review-thread resolution.
- Review-thread resolution requires its own exact operator approval and audit contract.
- No paid review spending.
- No merge, release, tag creation, or package publication.
- No continuous unattended loop or automatic retry of real executor invocations.
- No role assignment, agent-pool scheduling, GitHub issue assignment, shared runtime, or distributed lock claim.
- No named host adapter claim beyond generic local command evidence.
