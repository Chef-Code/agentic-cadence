# Tasks 18-22 Roadmap

> **For agentic workers:** Use `docs/roadmaps/2026-06-09-tasks-18-22-roadmap.md` as the public planning artifact after Tasks 13-17. Implement each task on its own branch and update the living docs with evidence before merge.

**Goal:** Move Agentic Cadence from read-only real-executor readiness toward a defensible real executor invocation boundary, without granting autonomous GitHub writes, merge, release, package-publication, distributed-lock, or agent-pool authority.

**Architecture:** Cadence remains the governor. Before a real executor process starts, Cadence should harden local audit integrity and approval identity, then produce an exact invocation plan. A later runner may start one approved executor process, but Git/PR materialization, merge, release, publication, role assignment, and scheduling remain separate governed actions.

**Tech Stack:** Python 3.11+, stdlib CLI, local JSON packets, append-only local audit evidence, Git, optional `gh` only for already-approved explicit evidence capture paths, `unittest`, GitHub Actions.

## Phase Ladder

Tasks 18-22 deliberately avoid jumping straight from readiness evidence to
unbounded process execution:

1. **Phase 3 hardening: Audit integrity** - make local audit evidence tamper-evident enough for future process-start decisions.
2. **Phase 3 hardening: Approval identity** - distinguish target-bound approval secrets from authenticated operator identity evidence.
3. **Phase 2 bridge: Invocation planning** - bind readiness, approval, adapter, timeout, environment, and result-path evidence into one read-only plan.
4. **Phase 2 side-effect boundary: Real executor start** - allow exactly one approved executor process only after the plan and readiness evidence are fresh.
5. **Phase 2 closeout bridge: Real run evidence** - bind real invocation records to result validation, epoch closeout, ownership closeout, and dry-run Git/PR planning.

## Task 18: Add Audit Hash-Chain Integrity Evidence

**Status:** Planned.

**Phase:** Phase 3 hardening before real process start.

**Why now:** `audit-replay` can identify corrupt or unsupported local audit records, but the audit stream still lacks tamper-evident linkage. Before Cadence treats any future real executor invocation as safe to start, local decisions and side-effect evidence need a deterministic chain that later sessions can replay.

**Likely files:**
- Modify: `codex_cadence/policy_audit.py`
- Modify: `codex_cadence/cli.py`
- Test: `tests/test_cadence.py`
- Docs: `README.md`, `docs/protocol.md`, `docs/autonomous-loop-readiness.md`, `docs/implementation-slices.md`, `docs/progress-log.md`, `docs/decision-log.md`

**Implementation outline:**
- Add a `cadence-audit-chain.v1` packet or extend `audit-replay.v1` with deterministic chain fields for supported audit event types.
- Add `previous_event_hash`, `event_hash`, and chain index metadata to newly appended audit records while treating older legacy records as explicit chain roots.
- Recheck chain continuity, event checksums, unsupported future record types, duplicate chain indexes, and missing predecessor hashes.
- Emit stable blockers such as `audit_chain_missing`, `audit_chain_broken`, `audit_event_hash_mismatch`, `audit_chain_index_duplicate`, and `unsupported_audit_chain_record`.

**Validation:**
- Clean legacy audit history can replay with an explicit legacy root.
- New chained records replay deterministically and report the final chain head.
- Missing predecessor hashes, modified event payloads, duplicate indexes, corrupt JSONL, and unsupported chain records block with stable codes.
- Existing audit append paths preserve rollback behavior when audit append fails.

## Task 19: Add Authenticated Operator Approval Identity Evidence

**Status:** Planned.

**Phase:** Phase 3 hardening before real process start.

**Why now:** Existing HMAC approval tokens bind approval to exact targets, but they do not identify an approver or provide a reusable approval-evidence contract for real executor invocation. A future real process start needs target-bound approval plus operator identity evidence, expiry, and purpose scoping before side effects begin.

**Likely files:**
- Create: `codex_cadence/approvals.py`
- Modify: `codex_cadence/cli.py`
- Modify: `codex_cadence/policy_audit.py`

**Implementation outline:**
- Add an `operator-approval.v1` verifier that consumes a target packet checksum, approval purpose, operator id, key id, issued-at time, expiration time, and signature/HMAC evidence.
- Scope purposes separately for `start_governed_execution`, `git_pr_materialization`, `real_executor_invocation`, and future release/package actions.
- Reject missing operator id, malformed timestamps, expired approval, future-issued approval, wrong purpose, wrong target checksum, weak key id, and unverifiable signature evidence with stable blockers.
- Add audit evidence for accepted approval verification without treating approval as executor, GitHub, merge, release, or package-publication authority.
- Keep external identity-provider integration out of scope; this slice defines local packet shape and verification semantics only.

**Validation:**
- Matching target checksum, purpose, operator id, key id, and fresh approval verifies successfully.
- Expired, future-issued, wrong-purpose, wrong-target, missing-operator, and malformed approvals block with stable codes.
- Approval verification does not start epochs, invoke executors, create branches, push, open PRs, merge, release, or publish packages.
- Existing target-bound HMAC approval paths remain backward compatible until migrated deliberately.

## Recommended Order

1. Task 18 adds audit hash-chain integrity before trusting future process-start evidence.
2. Task 19 adds authenticated operator approval identity before real executor approval is accepted.
3. Task 20 binds readiness, approval, audit, adapter, command, timeout, and result-path evidence into a read-only invocation plan.
4. Task 21 starts exactly one real executor process under the approved plan and records local invocation evidence.
5. Task 22 binds real invocation evidence to result validation, epoch closeout, ownership closeout, and dry-run Git/PR planning.

## Boundaries For All Five Tasks

- No hidden real executor invocation before Task 21.
- No process start without fresh readiness, approval, audit-chain, epoch, ownership, policy, timeout, and result-path evidence.
- No autonomous branch creation, commit, push, PR create/update, review-thread resolution, merge, release, or package publication.
- No dirty-worktree commit path; materialized changes remain evidence until a separately approved Git/PR path handles them.
- No paid review spending.
- No role assignment, agent-pool scheduling, GitHub issue assignment, shared runtime, or distributed lock claim.
- No named host adapter claim beyond the explicit generic adapter contract evidence implemented in the relevant slice.
