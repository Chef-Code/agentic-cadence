# Tasks 55-60 Roadmap

> **For agentic workers:** This roadmap starts from `main` after Task 54. Treat every slice as operator-gated controlled-loop work. Do not add unattended loop continuation, automatic GitHub writes, role assignment, executor retries, releases, package publication, or agent scheduling unless a future roadmap explicitly narrows and approves that behavior.

**Goal:** Move the controlled-loop runner from a read-only stage-execution approval target for stage 1 to a bounded, auditable, operator-gated single-stage execution path, then prepare read-only next-stage selection for stage N+1.

**Architecture:** Continue the existing packet chain. Each slice consumes prior packet artifacts, rechecks anchor checksums and sequence invariants, emits a new deterministic packet, and either remains read-only or performs exactly one approved command boundary. The work should keep stage execution separate from executor retry, Git/GitHub mutation, and loop continuation.

**Tech Stack:** Python CLI and packet validation in `codex_cadence`, focused pytest coverage in `tests/test_cadence.py`, and documentation updates in `README.md`, `docs/protocol.md`, `docs/implementation-slices.md`, `docs/autonomous-loop-readiness.md`, `docs/roadmap.md`, and `docs/progress-log.md`.

## Repo Position After Task 54

The repository now has a strong read-only control plane for the early loop-runner path:

- controlled runner start boundary evidence;
- controlled runner plan evidence;
- controlled runner dry-run evidence;
- controlled runner next-stage selection for stage 1;
- controlled runner stage-execution readiness, including an explicit approval target and non-execution guarantees.

The most important remaining gap is not more planning. The next gap is a safe transition from "stage 1 is selected and approval-targeted" to "one approved runner stage can be invoked, observed, and closed out without accidentally continuing the loop."

Still missing after Task 54:

- stage-execution approval packet consumption;
- exact approved stage invocation boundary;
- one-stage command execution with no retry and no loop continuation;
- post-stage output binding and closeout;
- read-only stage outcome planning;
- next-stage selection after a completed stage;
- autonomous branch, commit, push, PR creation, or GitHub mutation;
- distributed role assignment or agent scheduling;
- release, merge, or package publication automation.

## Phase Ladder

1. **Approval:** Convert the Task 54 approval target into a validated approval packet.
2. **Invocation Boundary:** Build a deterministic exact-command boundary before any process starts.
3. **Single Stage Execution:** Invoke exactly one approved stage command and capture evidence.
4. **Closeout:** Bind observed output to the approved stage and classify the stage result.
5. **Outcome Planning:** Decide the next operator-facing action from the stage result without acting on it.
6. **Next-Stage Selection:** Generalize read-only selection from stage 1 to stage N+1 after an accepted stage closeout.

## Task 55 - Controlled Runner Stage-Execution Approval

**Status:** Proposed

**Phase:** Approval
**Why now:** Task 54 emits a deterministic approval target but does not consume approval evidence. The next slice should prove that stage execution cannot proceed unless a specific approval packet matches the readiness target.

### Likely Command

`controlled-loop-runner-stage-execution-approval`

### Inputs

- `controlled-loop-runner-stage-execution-readiness.v1`
- `controlled-loop-runner-next-stage.v1`
- `controlled-loop-runner-start.v1`
- `controlled-loop-runner-plan.v1`
- `controlled-loop-runner-dry-run.v1`
- `operator-approval.v1`

### Implementation Outline

- Add a read-only CLI packet that consumes the Task 54 readiness packet and an operator approval packet.
- Verify the operator approval through the same `build_operator_approval_verification_packet` pattern used by existing approval-gated packets, including approval-secret-backed signature validation.
- Preserve approval identity, key id, signature, file path, file checksum, issued-at, and expires-at evidence without calling an audit-appending approval command.
- Recheck the full upstream runner chain:
  - runner start checksum and anchor identity;
  - plan checksum and approved stage catalog;
  - dry-run checksum and declared non-execution;
  - selected stage number and selected command;
  - readiness packet checksum and stage-execution approval target.
- Require the approval purpose to be `controlled_loop_runner_stage_execution`.
- Require the approval target checksum to match `stage_execution_approval_target_checksum`.
- Emit `controlled-loop-runner-stage-execution-approval.v1`.
- Keep the packet approval-only:
  - do not start a runner stage;
  - do not invoke an executor;
  - do not retry anything;
  - do not continue the loop;
  - do not append audit evidence;
  - do not write Git or GitHub state.

### Validation

- Matching readiness and approval succeeds.
- Wrong approval purpose fails.
- Wrong approval target checksum fails.
- Expired, future-dated, unsigned, bad-signature, or wrong-operator approval packets fail.
- Mutated approval file/checksum anchors fail.
- Mutated upstream runner start, plan, dry run, next-stage, or readiness packet fails.
- Packet output includes explicit non-execution guarantees.
- Tests prove no subprocess or audit write path is reached.

## Task 56 - Controlled Runner Stage Invocation Boundary

**Status:** Proposed

**Phase:** Invocation Boundary
**Why now:** After approval exists, the system still needs a final deterministic command boundary before process execution. This slice should make the exact stage command reviewable without starting it.

### Likely Command

`controlled-loop-runner-stage-invocation-boundary`

### Inputs

- `controlled-loop-runner-stage-execution-approval.v1`
- `controlled-loop-runner-stage-execution-readiness.v1`
- `controlled-loop-runner-next-stage.v1`
- `controlled-loop-runner-start.v1`
- `controlled-loop-runner-plan.v1`
- `controlled-loop-runner-dry-run.v1`

### Implementation Outline

- Add a read-only CLI packet that composes the exact stage invocation boundary.
- Recheck approval purpose, target checksum, readiness checksum, selected stage sequence, and selected command.
- Emit the exact argv array, command name, normalized arguments, working directory policy, evidence output policy, finite timeout policy, and deterministic invocation-boundary checksum.
- Bind the selected stage's `execution_authority` and `allowed_side_effects_when_executed` from the approved runner plan.
- Require the selected stage command to be one of the commands declared by the approved runner plan.
- Require the selected stage number to match the next-stage packet.
- Fail closed if the selected stage has no finite timeout or no declared side-effect policy.
- Explicitly mark that no process was started.
- Emit `next_controlled_action: execute_approved_runner_stage_once`.

### Validation

- Matching approval chain succeeds.
- Mutated selected command fails.
- Mutated stage number fails.
- Unknown stage command fails.
- Missing timeout or missing side-effect policy fails.
- Boundary checksum is stable.
- Packet guarantees no subprocess start, no audit append, no Git/GitHub mutation, and no loop continuation.

## Task 57 - Controlled Runner Single-Stage Execution

**Status:** Proposed

**Phase:** Single Stage Execution
**Why now:** The runner cannot become operational until it can execute one approved internal stage command. This must be deliberately narrower than loop continuation.

### Likely Command

`controlled-loop-runner-stage-execute`

### Inputs

- `controlled-loop-runner-stage-invocation-boundary.v1`
- `controlled-loop-runner-stage-execution-approval.v1`
- `controlled-loop-runner-stage-execution-readiness.v1`
- full upstream runner chain evidence referenced by the boundary packet

### Implementation Outline

- Add a CLI command that invokes exactly one approved runner stage command.
- Before invocation, recheck the complete approval and boundary chain.
- Execute only the exact argv represented by the boundary packet, with `shell=False`, no shell expansion, no compound commands, and the fixed working-directory policy declared by the boundary.
- Require the selected internal Cadence CLI stage command named by the boundary packet to match the approved runner plan.
- Pass only the normalized arguments represented by the boundary packet.
- Capture stdout, stderr, exit code, output packet path if applicable, started-at timestamp, completed-at timestamp, and a command-result checksum.
- Emit `controlled-loop-runner-stage-execution.v1`.
- Append no audit for pre-start validation failures.
- After a process is started, append at most one deterministic audit record for the stage execution attempt if the existing audit model requires command execution evidence; include boundary, approval, stage, and command-result checksums.
- Verify observed side effects remain within the selected stage's `allowed_side_effects_when_executed`.
- Enforce hard boundaries:
  - no executor retry;
  - no second stage;
  - no loop continuation;
  - no role assignment;
  - no Git/GitHub write;
  - no merge, release, or package publication;
  - no agent scheduling.

### Validation

- Approved boundary executes the selected command once.
- A failing stage command produces terminal evidence and does not retry.
- A mutated boundary fails before process start.
- An unapproved command fails before process start.
- Shell strings, compound commands, cwd escapes, and undeclared side effects fail.
- Tests prove only one subprocess invocation is attempted.
- Tests prove no continuation command is called after stage completion.

## Task 58 - Controlled Runner Stage Closeout

**Status:** Proposed

**Phase:** Closeout
**Why now:** A stage execution record is not enough. The runner needs a separate packet that validates observed output against the approved stage and classifies the result without selecting another stage.

### Likely Command

`controlled-loop-runner-stage-closeout`

### Inputs

- `controlled-loop-runner-stage-execution.v1`
- `controlled-loop-runner-stage-invocation-boundary.v1`
- `controlled-loop-runner-stage-execution-approval.v1`
- upstream runner chain evidence referenced by the execution packet
- stage output packet produced by the selected stage command when required by the approved evidence output policy

### Implementation Outline

- Add a CLI packet that validates stage execution evidence.
- Recheck selected stage number, selected command, invocation checksum, approval checksum, and upstream runner chain checksums.
- Derive required stage output evidence from the approved stage and invocation boundary policies.
- If output evidence is required, load it and verify its checksum against the execution record.
- If output evidence is not required, record that no output packet was expected rather than treating the absence as success by default.
- Classify stage result as `completed`, `failed`, or `blocked`.
- Emit `controlled-loop-runner-stage-closeout.v1`.
- Do not choose the next stage and do not continue the loop.
- Emit explicit next action:
  - `plan_controlled_runner_stage_outcome` for completed or blocked stages;
  - `inspect_controlled_runner_stage_failure` for failed stages.

### Validation

- Successful stage output binds to closeout.
- Missing expected output packet fails.
- Mismatched output checksum fails.
- Non-zero exit code produces `failed` closeout and no retry.
- Mutated execution evidence fails.
- Packet guarantees no next-stage selection, no retry, no Git/GitHub write, and no continuation.

## Task 59 - Controlled Runner Stage Outcome Plan

**Status:** Proposed

**Phase:** Outcome Planning
**Why now:** Once a stage is closed out, the system needs a read-only planner that decides what the operator should do next. This keeps continuation policy separate from execution.

### Likely Command

`controlled-loop-runner-stage-outcome-plan`

### Inputs

- `controlled-loop-runner-stage-closeout.v1`
- `controlled-loop-runner-stage-execution.v1`
- `controlled-loop-runner-stage-invocation-boundary.v1`
- `controlled-loop-runner-stage-execution-approval.v1`
- `controlled-loop-runner-stage-execution-readiness.v1`
- `controlled-loop-runner-next-stage.v1` or `controlled-loop-runner-next-stage-continuation.v1`
- `controlled-loop-runner-plan.v1`
- `controlled-loop-runner-dry-run.v1`
- `controlled-loop-runner-start.v1`

### Implementation Outline

- Add a read-only CLI packet that evaluates the closed-out stage against the approved runner plan.
- Recheck the closeout, execution, invocation, approval, readiness, next-stage, start, plan, and dry-run chain.
- If the stage completed and more stages exist, emit a deterministic target for next-stage selection.
- If the stage completed and no stages remain, emit a deterministic target for controlled runner completion.
- If the stage failed or blocked, emit a deterministic target for operator inspection or a future operator-gated retry-planning target only.
- Emit `controlled-loop-runner-stage-outcome-plan.v1`.
- Do not select the next stage, execute a retry, continue the loop, or append audit evidence.

### Validation

- Completed non-final stage emits next-stage selection target.
- Completed final stage emits completion target.
- Failed stage emits inspection target and no retry.
- Blocked stage emits inspection target and no retry.
- Mutated stage closeout or runner plan fails.
- Packet output includes explicit read-only and non-continuation guarantees.

## Task 60 - Controlled Runner Next-Stage Continuation Selection

**Status:** Proposed

**Phase:** Next-Stage Selection
**Why now:** Task 53 selected stage 1 from the initial runner dry run. After a completed stage, the runner needs the same read-only selection discipline for stage N+1 without turning into an unattended loop.

### Likely Command

`controlled-loop-runner-next-stage-continuation`

### Inputs

- `controlled-loop-runner-stage-outcome-plan.v1`
- `controlled-loop-runner-stage-closeout.v1`
- `controlled-loop-runner-stage-execution.v1`
- `controlled-loop-runner-plan.v1`
- `controlled-loop-runner-dry-run.v1`
- `controlled-loop-runner-start.v1`

### Implementation Outline

- Add a read-only CLI packet that selects the next stage after a completed prior stage.
- Require the outcome plan to authorize next-stage selection, not completion, retry, or inspection.
- Require prior stage closeout status to be `completed`.
- Select exactly stage `previous_stage_number + 1`.
- Recheck that the selected continuation stage exists in the approved runner plan.
- Reuse the Task 53 selection invariants where possible, generalized for stage N+1.
- Emit `controlled-loop-runner-next-stage-continuation.v1`.
- Do not emit a stage-execution readiness target from this selection packet.
- Do not claim the existing Task 54 readiness command can be rerun against continuation selection; that command is stage-1-only until a future slice explicitly generalizes readiness for `controlled-loop-runner-next-stage-continuation.v1`.
- Emit `next_controlled_action: generalize_controlled_runner_stage_execution_readiness_for_continuation`.
- Do not execute the selected stage.
- Do not automatically recurse into readiness, approval, invocation, or execution.

### Validation

- Completed stage 1 selects stage 2 when stage 2 exists.
- Completed final stage refuses next-stage selection and points to completion planning.
- Failed or blocked closeout refuses continuation.
- Mutated outcome plan or closeout fails.
- Stage sequence gaps fail.
- Packet contains no readiness target and does not invoke or authorize the stage-1 readiness command for continuation packets.
- Packet guarantees no execution, no retry, no Git/GitHub write, and no loop continuation.

## Recommended Order

1. Task 55: approval packet for the Task 54 readiness target.
2. Task 56: read-only exact invocation boundary.
3. Task 57: execute one approved stage command.
4. Task 58: validate and close out the observed stage result.
5. Task 59: plan the next operator action from the closeout.
6. Task 60: select stage N+1 after a completed stage.

## Boundaries For All Six Tasks

- Unattended loop continuation remains out of scope.
- Automatic executor retry must not be added.
- Automatic Git branch, commit, push, PR, merge, release, or package publication behavior remains disallowed.
- Role assignment and agent scheduling stay outside these slices.
- Read-only packets must never append audit evidence.
- Read-only packets must never start a process.
- A stage execution command may run only one selected stage.
- Stage closeout must not select or execute the next stage.
- Existing checksum, anchor, and sequence validation must not be weakened.
- Keep every new packet deterministic enough for fixture-based tests.
