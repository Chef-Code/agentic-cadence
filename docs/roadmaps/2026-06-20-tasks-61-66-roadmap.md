# Tasks 61-66 Roadmap

> **For agentic workers:** This roadmap starts from `main` after Task 60. Treat every slice as operator-gated controlled-loop runner work. Do not add unattended loop continuation, automatic GitHub writes, automatic executor retries, role assignment, release, merge, package publication, or agent scheduling unless a future roadmap explicitly narrows and approves that behavior.

**Goal:** Move the controlled-loop runner from read-only stage `N+1` selection to a bounded continuation-stage execution path that preserves stage-input, approval, side-effect, and closeout boundaries.

**Architecture:** Continue the existing packet chain, but add a small stage-input binding step before generalized continuation readiness. Stage 2 is `start-governed-execution`, so the runner must bind the prior `loop-run-plan` output, executor task packet, and explicit approval evidence before it can prepare an invocation boundary. Each task should consume saved evidence, recheck checksums and sequence invariants, emit deterministic packets, and stop before the next authority boundary.

**Tech Stack:** Python CLI and packet validation in `codex_cadence`, focused pytest coverage in `tests/test_cadence.py`, and documentation updates in `README.md`, `docs/protocol.md`, `docs/implementation-slices.md`, `docs/autonomous-loop-readiness.md`, `docs/roadmap.md`, and `docs/progress-log.md`.

The most important remaining gap is not to recurse automatically. The next gap is to prove that a selected continuation stage can be prepared without losing the input and approval gates that the selected command requires.

- autonomous branch, commit, push, PR creation, or GitHub mutation;
- distributed role assignment or agent scheduling;
- release, merge, or package publication automation.

## Phase Ladder

1. **Stage Input Binding:** Bind selected continuation stage dependencies to saved prior-stage output before readiness.
2. **Continuation Readiness:** Generalize stage-execution readiness to consume continuation selection and bound inputs.
3. **Continuation Approval:** Verify stage-execution approval and any command-specific approval dependencies.
4. **Continuation Invocation Boundary:** Build the exact command boundary for the selected continuation stage.
5. **Continuation Execution:** Execute exactly one approved continuation stage with declared side effects only.
6. **Continuation Closeout And Outcome:** Validate the observed stage result and plan the next operator action without selecting or executing it.

## Task 61 - Controlled Runner Stage Input Binding For Continuation

**Status:** Completed

**Phase:** Stage Input Binding
**Why now:** Task 60 can select stage 2, and stage 2 is `start-governed-execution`. That command cannot be invoked from the runner plan alone; it needs a concrete executor task file and explicit approval evidence derived from the prior `loop-run-plan` output. The next slice should bind those inputs before readiness or invocation logic can claim continuation support.

### Likely Command

`controlled-loop-runner-stage-input-binding`

### Inputs

- `controlled-loop-runner-next-stage-continuation.v1`
- `controlled-loop-runner-stage-outcome-plan.v1`
- `controlled-loop-runner-stage-closeout.v1`
- `controlled-loop-runner-stage-execution.v1`
- prior stage output packet, initially `loop-run-plan.v1`
- operator-supplied executor task file extracted from the prior stage output when the selected stage is `start-governed-execution`
- `controlled-loop-runner-start.v1`
- `controlled-loop-runner-plan.v1`
- `controlled-loop-runner-dry-run.v1`

### Implementation Outline

- Add a read-only packet that binds the selected continuation stage to the saved evidence it needs before readiness.
- Require the continuation packet to be valid, selected, read-only, and still recommending `generalize_controlled_runner_stage_execution_readiness_for_continuation`.
- Recheck the continuation packet against the saved outcome plan, closeout, execution, runner-start, runner-plan, and dry-run evidence.
- Load the prior stage output referenced by the completed stage execution and closeout.
- Reconcile the current `loop-run-plan.v1` output contract before binding:
  - real `loop-run-plan.v1` packets must be accepted by stage closeout without requiring a `valid: true` field they do not currently emit; or
  - `loop-run-plan.v1` must explicitly emit that field with protocol and test coverage before Task 61 relies on it.
- For `start-governed-execution`, require the prior `loop-run-plan.v1` output to contain a schema-valid `generic-executor-task.v1` payload or fail closed with a stable blocker.
- Require the prior `loop-run-plan.v1` output to be semantically waiting for executor-task approval, including `recommended_next_action: request_operator_approval`, a matching executor task checksum, and planned steps that point to `start-governed-execution` without showing executor or epoch start.
- Require an operator-supplied executor task file whose JSON content exactly matches the executor task embedded in the prior `loop-run-plan.v1` output.
- Record the executor task checksum, file path, expected approval target checksum, and selected continuation stage checksum.
- Do not generate or reveal an approval token in this packet.
- Emit `controlled-loop-runner-stage-input-binding.v1`.
- Emit `next_controlled_action: prepare_controlled_runner_continuation_stage_execution_readiness`.
- Do not prepare readiness, approve execution, start a process, start an epoch, append audit evidence, write Git/GitHub state, or continue the loop.

### Validation

- Completed stage 1 output containing a schema-compatible `loop-run-plan.v1` packet and schema-valid executor task binds to stage 2 input evidence.
- The current `loop-run-plan.v1`/stage-closeout output identity mismatch is resolved by code and protocol tests before binding succeeds.
- Missing prior stage output fails.
- Prior stage output without an executor task fails for `start-governed-execution`.
- Prior stage output that is not waiting for executor-task approval fails.
- Executor task checksum drift or planned-step mismatch fails.
- Executor task file content mismatch fails.
- Mutated continuation, closeout, execution, runner-start, runner-plan, or dry-run evidence fails.
- Packet contains no approval token and starts no process.
- Packet guarantees no audit append, no epoch start, no Git/GitHub write, and no loop continuation.

### Implementation Notes

- Added `controlled-loop-runner-stage-input-binding` as a read-only packet
  between continuation selection and continuation readiness.
- Fixed stage closeout identity for real `loop-run-plan.v1` packets, which do
  not emit a top-level `valid` field.
- Binding is currently scoped to stage-2 `start-governed-execution` inputs:
  the prior `loop-run-plan` must be waiting for executor-task approval, its
  embedded executor task checksum must match, planned steps must target
  `start-governed-execution`, and the supplied executor task file must match
  the embedded task exactly.
- The command records the executor task checksum and expected executor-task
  approval target checksum, but emits no approval token and does not prepare
  readiness, start a process, start an epoch, append audit evidence, write
  Git/GitHub state, or continue the loop.

## Task 66 - Controlled Runner Continuation Stage Closeout And Outcome Planning

**Status:** Proposed

**Phase:** Continuation Closeout And Outcome
**Why now:** Executing a continuation stage is not enough. The runner needs to validate the observed output, classify the stage, and plan the next operator action without selecting another stage or continuing automatically.

### Likely Commands

- `controlled-loop-runner-stage-closeout`
- `controlled-loop-runner-stage-outcome-plan`

### Inputs

- `controlled-loop-runner-stage-execution.v1`
- `controlled-loop-runner-stage-invocation-boundary.v1`
- `controlled-loop-runner-stage-execution-approval.v1`
- `controlled-loop-runner-stage-execution-readiness.v1`
- `controlled-loop-runner-next-stage-continuation.v1`
- `controlled-loop-runner-stage-input-binding.v1`
- upstream runner chain evidence referenced by the execution packet
- stage output packet produced by the selected stage command when required by the approved evidence output policy

### Implementation Outline

- Generalize stage closeout to consume continuation-backed execution evidence.
- Preserve existing stage 1 closeout behavior.
- Recheck selected stage number, selected command, invocation checksum, approval checksum, readiness checksum, continuation checksum, input-binding checksum, and upstream runner chain checksums.
- Derive required stage output evidence from the approved stage and invocation boundary policies.
- For `start-governed-execution`, require valid `execution-start.v1` output and bind it to the execution result checksum.
- Classify the stage result as `completed`, `failed`, or `blocked`.
- Generalize stage outcome planning to consume continuation-backed closeout and stage-selection evidence.
- If the continuation stage completed and more stages exist, emit a deterministic target for next-stage continuation selection.
- If the continuation stage completed and no stages remain, emit a deterministic target for future controlled runner completion evidence.
- If the continuation stage failed or blocked, emit an inspection target plus a future operator-gated retry-planning target only.
- Do not select the next stage, execute a retry, start an executor, continue the loop, append audit evidence from read-only outcome planning, or write Git/GitHub state.

### Validation

- Successful `start-governed-execution` output binds to continuation closeout.
- Missing expected output packet fails.
- Mismatched output checksum fails.
- Non-zero exit code produces failed closeout and no retry.
- Mutated execution, boundary, approval, readiness, continuation, input-binding, or runner-plan evidence fails.
- Completed non-final continuation stage emits next-stage selection target only.
- Completed final continuation stage emits runner-completion target only.
- Packet guarantees no next-stage selection, no retry, no Git/GitHub write, and no continuation.

## Boundaries For All Six Tasks

- Unattended loop continuation remains out of scope.
- Automatic executor retry must not be added.
- Automatic Git branch, commit, push, PR, merge, release, or package publication behavior remains disallowed.
- Role assignment and agent scheduling stay outside these slices.
- Read-only packets must never append audit evidence.
- Read-only packets must never start a process.
- A stage execution command may run only one selected stage.
- Stage closeout must not select or execute the next stage.
- Outcome planning must not select or execute the next stage.
- Existing checksum, anchor, and sequence validation must not be weakened.
- Existing stage 1 behavior must remain backward compatible unless a test proves a stricter gate is necessary.
- Keep every new packet deterministic enough for fixture-based tests.
