# Tasks 23-27 Roadmap

> **For agentic workers:** Use `docs/roadmaps/2026-06-11-tasks-23-27-roadmap.md` as the public planning artifact after Tasks 18-22. Implement each task on its own branch and update the living docs with evidence before merge.

**Goal:** Move Agentic Cadence from governed real-executor evidence toward a controlled single-tick loop that can chain existing packet gates without granting autonomous GitHub writes, dirty-worktree commit authority, merge, release, package-publication, distributed-lock, or agent-pool authority.

**Architecture:** Cadence remains the governor. The next slices should compose the existing local evidence contracts before adding new authority: snapshot, candidate election, ownership, approval, invocation plan, real invocation, result validation, closeout, and dry-run Git/PR planning. Live GitHub writes stay behind the existing exact operator-approved materialization path.

**Tech Stack:** Python 3.11+, stdlib CLI, local JSON packets, append-only local audit evidence, Git, optional `gh` only for already-approved explicit evidence capture/materialization paths, `unittest`, GitHub Actions.

## Phase Ladder

Tasks 23-27 deliberately compose existing authority before expanding it:

1. **Phase 1 bridge: Single controlled loop tick** - orchestrate one bounded local cycle through existing evidence gates.
2. **Phase 4/5 closeout hygiene: Ownership closeout after accepted run closeout** - make ownership lifecycle evidence follow completed governed work without hidden role or distributed-lock claims.
3. **Phase 4 Git/PR preparation: Dirty-worktree materialization evidence** - turn accepted materialized changes into a reviewed Git/PR materialization input without silent commits.
4. **Phase 5 feedback freshness: Saved PR evidence freshness bridge** - preserve PR evidence freshness labels into write-side planning and response planning.
5. **Phase 5 feedback candidates: Review follow-up candidate generation** - convert actionable review feedback into bounded execution candidates without writing to GitHub.

## Task 23: Add Controlled Single-Tick Run Packet

**Status:** Implemented in `main` via PR #92.

**Phase:** Phase 1 bridge after real invocation closeout.

**Why now:** Cadence has enough local evidence packets to run a single controlled cycle, but no command composes them end to end. A single-tick packet should prove the orchestration boundary before any continuous loop or unattended retry behavior exists.

**Likely files:**
- Modify: `codex_cadence/cli.py`
- Modify: `codex_cadence/model.py`
- Modify: `codex_cadence/executor_invocation.py`
- Modify: `codex_cadence/policy_audit.py`
- Test: `tests/test_cadence.py`
- Docs: `README.md`, `docs/protocol.md`, `docs/autonomous-loop-readiness.md`, `docs/implementation-slices.md`, `docs/progress-log.md`, `docs/session-handoff.md`

**Implementation outline:**
- Add `controlled-loop-tick`, which consumes existing local evidence files rather than rediscovering mutable state mid-flow.
- Chain `loop-tick`, candidate/task evidence, governed execution-start, invocation readiness, invocation plan, real invocation record, result evidence, snapshot-after, closeout, and optional dry-run Git/PR plan anchors.
- Reuse existing commands/contracts for validation; do not duplicate low-level checks.
- Emit `controlled-loop-tick.v1` with step checksums, step statuses, blockers, next decision, and side effects.
- Append audit evidence only after the packet is internally consistent.
- Do not loop continuously, retry failed real executor invocations, create branches, commit, push, open/update PRs, resolve review threads, merge, release, publish packages, assign roles, schedule agents, or claim distributed locks.

**Implemented evidence:**
- `controlled-loop-tick` requires existing saved `--loop-tick-file`,
  `--task-file`,
  `--execution-start-file`, `--readiness-file`, `--invocation-plan-file`,
  `--real-invocation-file`, `--result-file`, `--snapshot-after-file`, and
  `--closeout-file`, plus optional `--git-pr-plan-file` when that file is a
  review-ready, non-authorizing dry-run Git/PR plan.
- Completed packets append `controlled_loop_tick` audit evidence and record
  `controlled_loop_tick_audit_appended`; blocked packets append no audit
  record.
- Stable limitations include `composes_existing_local_evidence_only`,
  `does_not_retry_executor`, and
  `does_not_rewrite_invocation_or_closeout_records`.
- `controlled_loop_tick_audit_append_failed` blocks the packet and recommends
  `recover_controlled_tick_audit` if the success-only audit append fails after
  internal validation.

**Validation:**
- Matching local evidence can produce a completed single-tick packet.
- Missing or mismatched saved task/start/readiness/plan/invocation/result/snapshot/closeout evidence blocks with stable codes before additional mutation; ownership and approval remain validated by the earlier readiness/plan evidence rather than by direct controlled-loop inputs.
- Existing closeout and invocation records are not rewritten by the orchestration packet itself.
- A failed or blocked executor result produces a terminal local decision without GitHub writes.
- The command cannot re-run a real executor just because a prior invocation record is invalid.

## Task 24: Add Closeout-Bound Ownership Completion Evidence

**Status:** Implemented in `main` via PR #93.

**Phase:** Phase 4 local ownership lifecycle hardening.

**Why now:** Real-invocation closeout revalidates active ownership, but it does not close ownership records. Before a controlled loop can hand off cleanly, Cadence needs an explicit packet that binds completed epoch/task evidence to local ownership closeout without claiming distributed locks or role assignment authority.

**Likely files:**
- Modify: `codex_cadence/ownership.py`
- Modify: `codex_cadence/cli.py`
- Modify: `codex_cadence/policy_audit.py`
- Test: `tests/test_cadence.py`, `tests/test_audit_replay.py`
- Docs: `README.md`, `docs/protocol.md`, `docs/implementation-slices.md`, `docs/progress-log.md`

**Implementation outline:**
- Add a closeout helper or command mode that consumes accepted executor closeout evidence plus an active `work-ownership.v1` record.
- Recheck ownership id, task id, candidate id, role, claimer, repo, branch, `HEAD`, epoch id, closeout status, and closeout checksum.
- Move the local ownership record to closed only after those anchors match.
- Append replayable ownership mutation audit evidence for closeout-bound completion.
- Keep manual `close-work-ownership` and `fail-work-ownership` behavior compatible.
- Do not assign roles, schedule agents, claim remote locks, write GitHub issues, or infer review authority.

**Validation:**
- Matching completed closeout evidence closes the active ownership record.
- Wrong epoch, task, claimer, role, branch, `HEAD`, or closeout checksum blocks before moving the record.
- Failed executor closeout can fail ownership through the existing explicit failure path only when requested.
- Audit append failure rolls back the ownership move.
- Implemented as `complete-work-ownership-from-closeout`, with optional
  `work_ownership_mutation` audit anchors for `executor_closeout_file`,
  `executor_closeout_checksum`, and `executor_closeout_status`, plus a saved
  closeout `task_checksum` recheck before ownership anchors are trusted.

## Task 25: Add Dirty-Worktree Git/PR Materialization Plan Binding

**Status:** Implemented in `main` via PR #94.

**Phase:** Phase 4 Git/PR preparation after materialized real runs.

**Why now:** `invoke-real-executor --side-effect-mode materialized_changes` can leave reviewed dirty worktree evidence, and closeout can bind it. The current live Git/PR materialization path expects an already-materialized current commit. A bridge packet should convert accepted dirty-worktree evidence into an explicit reviewed materialization input without silently committing.

**Likely files:**
- Modify: `codex_cadence/git_pr_plan.py`
- Modify: `codex_cadence/cli.py`
- Modify: `codex_cadence/executor_invocation.py`
- Test: `tests/test_git_pr_plan.py`, `tests/test_cadence.py`
- Docs: `README.md`, `docs/protocol.md`, `docs/implementation-slices.md`, `docs/progress-log.md`

**Implementation outline:**
- Add a dry-run packet that binds closeout-approved materialized-change evidence to a proposed commit plan.
- Recheck dirty-worktree fingerprint checksum, file list, allowed paths, branch policy, base branch, PR body preflight, and current repo state.
- Emit exact proposed commit metadata and operator-approval target checksum.
- Keep the actual commit/push/PR write behind a later exact approval or the existing materialization command.
- Do not auto-stage, auto-commit, push, create/update PRs, resolve review threads, merge, release, or publish packages.

Implemented command/packet:
- `git-pr-dirty-materialization-plan`
- `git-pr-dirty-materialization-plan.v1`
- `closeout_invocation_mismatch`
- `dirty_worktree_fingerprint_mismatch`
- `materialized_change_files_mismatch`

**Validation:**
- Matching dirty-worktree fingerprint evidence yields a dry-run commit/PR materialization plan.
- Same-file content edits after invocation block via fingerprint mismatch.
- Extra dirty files, branch drift, base-branch drift, PR-body failures, or branch-policy violations block.
- The command leaves the worktree unchanged.

## Task 27: Generate Review Follow-Up Candidates From Saved Threads

**Status:** Implemented in `main` via PR #96.

**Phase:** Phase 5 feedback into candidate discovery.

**Why now:** Cadence can read saved review-thread evidence and plan responses, but candidate discovery only partially turns PR state into executable follow-up work. Review comments need to become bounded candidates with stable provenance before a loop can select them safely.

**Likely files:**
- Modify: `codex_cadence/candidates.py`
- Modify: `codex_cadence/review_response.py`
- Modify: `codex_cadence/pr_readiness.py`
- Test: `tests/test_candidates.py`, `tests/test_cadence.py`
- Docs: `README.md`, `docs/protocol.md`, `docs/implementation-slices.md`, `docs/progress-log.md`

**Implementation outline:**
- Convert unresolved actionable current review-thread comments from saved evidence into execution candidates.
- Preserve source PR, thread id, comment id, path, line, author, freshness label, and suggested target files.
- Ignore resolved, outdated, non-actionable summary, and bot walkthrough comments.
- Group duplicate comments by stable follow-up target when possible.
- Keep response execution read-only; do not post comments, resolve threads, update PR bodies, invoke paid review, or start executors.

**Validation:**
- Unresolved actionable review comments become candidates with stable ids and provenance.
- Resolved, outdated, summary-only, and non-actionable comments are ignored.
- Malformed or incomplete review-thread evidence blocks candidate creation.
- Candidate discovery can rank review follow-ups without bypassing approval, ownership, or executor gates.

Implemented evidence:
- Saved review-thread candidates preserve source PR number/URL when present,
  thread id, comment id or grouped comment ids, author, path, line, freshness
  label, and target files.
- Incomplete or malformed saved review-thread evidence blocks discovery with
  `review_thread_evidence_incomplete` and `refresh_review_thread_evidence`.
- `github-evidence-sync` copies the already-read PR number and URL into saved
  review-thread evidence so later local candidate discovery can preserve source
  PR identity without another GitHub call.

## Recommended Order

1. Task 23 composes existing local evidence into one controlled tick packet.
2. Task 24 closes local ownership evidence only after accepted closeout evidence.
3. Task 25 prepares dirty-worktree materialization without silently committing.
4. Task 26 preserves saved PR freshness before any write-side planning trusts it.
5. Task 27 turns actionable review feedback into bounded candidates.

## Boundaries For All Five Tasks

- No continuous unattended loop.
- No automatic retry of real executor invocations.
- No autonomous branch creation, commit, push, PR create/update, review-thread resolution, merge, release, or package publication.
- No dirty-worktree commit path without a separate exact approval gate.
- No paid review spending.
- No role assignment, agent-pool scheduling, GitHub issue assignment, shared runtime, or distributed lock claim.
- No named host adapter claim beyond generic local command evidence.
